# 欧洲交通路线查找（Europe Route Finder）

## 为什么需要这个 skill

Google Maps、Omio、Interrail 都只在「出发站 → 目的站」之间算路线，所以经常漏掉更好的方案，比如：

- 莱比锡 → 布达佩斯：德累斯顿有直达布达佩斯的夜车，先坐德铁到德累斯顿就行，但很多平台搜不到。
- 莱比锡 → 法国阿尔卑斯滑雪站 Les Arcs（山下火车站 Bourg-Saint-Maurice）：直觉是「去日内瓦中转」，但日内瓦住宿贵、瑞士火车贵、日内瓦到雪场的接驳也贵（FlixBus 65€）。更好的做法是：第一天莱比锡 → 伯尔尼（DB 约 41€），住一晚青旅女生间（Booking 会员价约 33€）；第二天坐 FlixBus **越过日内瓦**到法国安纳西（约 14.50€），换大区班车 Y51 到阿尔贝维尔（按区段约 2–8€），再坐 TER 到 Bourg-Saint-Maurice（约 13.60€），持火车票缆车冬季免费上山。全程约 105–110€，中午就到，每一段都有好几班车可以后备，比飞机、夜车、经日内瓦坐接驳都便宜，而且晚上睡在床上。这条路线是用户自己在 Google 地图上找到的，比当时 skill 算出来的「伯尔尼 → 尚贝里 → TER」还快 2 小时、便宜约 10€——大区班车这种小交通，订票网站基本搜不到。同样的接法也适用于日内瓦过夜（日内瓦 → 安纳西 FlixBus 约 9€ → Y51 → TER，约 114–120€，比经尚贝里便宜、早 2 小时到）和安纳西过夜（直接坐 Y51）。另外，布鲁塞尔的滑雪夜车（周五 20:16 → 周六 09:09 Bourg-Saint-Maurice）6 人 couchette 183€，加上莱比锡 → 布鲁塞尔约 80€，总价约 263€，是最贵但最省心的一条：不用住青旅、不用早起、上午就到。

另外比价平台的价格往往不是官方价（例如同一天莱比锡 → 日内瓦，Omio 约 80€，bahn.de 加 BahnCard 25 是 41€）；跨境车由几国铁路联合运营，会在多个国家的官网上架，同一班车在不同官网价格不一样。

这个 skill 的思路是：**把两端都扩展成「枢纽城市集合」，在枢纽之间找最直接的干线；把行程拆成「第一天长途到一个便宜的过夜城市 + 第二天短途」来考虑；第二天用白天的大巴跨过贵的国家和贵的门户城市，直接接上目的地那条铁路线；再查各平台和各官网的真实价格，把住宿（青旅）和最后一段也算进总价，并告诉用户每一段在哪里买最便宜。**

回复和 HTML 页面都用中文。

## 用户的固定情况

开始前先读同目录下的 **`profile.md`**：里面是用户的出发地、持有的车票和折扣卡、住宿偏好、不能接受的交通方式、换乘上限等。下面各步说到「用户的固定情况」都指这个文件。没有 `profile.md` 时，在第 0 步一起问用户。

## 第 0 步：确认输入

| 项 | 说明 | 缺失时 |
|---|---|---|
| 出发地 | | 默认莱比锡 |
| 最终目的地 | 可以是小镇、滑雪场、景点、某个营地的具体地址 | 必须问 |
| 最晚到达时间 | 例如「19 号 18:00 前」。问清楚这是硬性的（比如营地报到截止）还是理想时间 | 必须问；用户记不清时，按保守和宽松两个时间分别给结果，并提醒用户去核对（例如营地的行前通知） |
| 出发日期范围 | 理想出发日 + 前后可接受的范围 | 根据最晚到达时间倒推；只给一天时默认看前后各 1 天 |
| 用户自己想到的方案 | 用户常常已经有一个候选方案或参考价格 | 有就记下，作为对比基准一起查 |
| 人数 | | 默认 1 人 |
| 行李 | 例如滑雪装备、大箱子（影响飞机和大巴） | 默认普通行李 |

把缺的项合并成一次提问（有提问工具就用，例如 Claude 的 AskUserQuestion），不要一项一项问。有合理默认值的就直接用，并在结果里写明。

**用户给出自己的方案时**，必须把它作为一条路线完整查一遍价格和时刻，放进对比表，并顺着它的思路找变体（换一个过夜城市、大巴坐到另一个站）。如果查下来它或它的变体最好，就直接说；如果有问题（赶不上到达时间、某班车售罄），具体说出卡在哪一段。

## 第 1 步：两端扩展成枢纽集合

**目的地端**
1. 判断目的地有没有火车站、有没有干线（长途/国际）列车停靠。
2. **定位「最后一个火车站」和它所在的铁路线。** 例如 Les Arcs 的最后一个火车站是 Bourg-Saint-Maurice，在塔兰塔斯线上：Chambéry → Albertville → Moûtiers → Aime → Bourg-Saint-Maurice，往外连着里昂和安纳西。把这条线上、或能直达这条线的车站都列出来——它们都是第二天可以「接上」的点，不要只盯着最有名的大城市或机场。
   - **接入点不只是火车站。** 很多不在铁路线上的城市有大区班车开到线上的车站，例如安纳西不在塔兰塔斯线上，但大区班车 Y51（cars Région / Altibus）每 1–2 小时一班开到阿尔贝维尔火车站。这类班车便宜、班次多，却几乎不会出现在 DB、SNCF、Omio 的结果里，要专门用 Google 地图公交模式或当地大区交通网站查。
3. **查清最后一段**：从最后一个火车站到目的地怎么走（缆车、当地大巴、站间巴士），时长、班次、首末班和价格。特别查有没有**和火车票联动的优惠**：很多雪场冬季凭当天的 SNCF 火车票免费坐缆车或接驳（例如 Les Arcs 缆车凭 SNCF 票免费，否则往返 5€），这会让「坐火车到山下」比「坐接驳大巴直接上山」更划算。
4. **门户城市和接驳**：最近的大城市/机场（例如日内瓦、里昂）以及它们到目的地的直达大巴或接驳。营地、滑雪学校、度假村常有指定的接驳车（有时就是 FlixBus 或某家大巴公司的固定站点），要专门搜，但它们常常是最贵的一种，只作为对比项。
5. **再往外扩一圈：找「过夜枢纽」。** 门户城市、门户周边的小城，和更远一些但住宿便宜、从出发地坐火车方便、并且有白天大巴去目的地铁路线的城市，都是候选。例：去法国阿尔卑斯的过夜枢纽有伯尔尼、日内瓦、安纳西、洛桑、里昂。哪个最便宜往往取决于当晚的青旅价格，必须按第 5 步实查，不能凭印象。
6. 挑 3–5 个最有希望的过夜枢纽和接入站。

**出发地端**
1. 以莱比锡为例：莱比锡、哈勒、德累斯顿、柏林、爱尔福特、纽伦堡，夜车时也可考虑布拉格等。
2. 记下从出发地到每个枢纽的时间和费用。用户有 Deutschlandticket，坐区域车去德累斯顿、爱尔福特、哈勒等是 0 元，这类「先坐区域车到附近大城市再上干线」的方案要优先考虑。
3. 出发端枢纽只有在能带来好处时才值得用：有直达车、有夜车、明显更便宜或更少换乘。

## 第 2 步：拼出候选路线

### 一定要考虑的路线形态

1. **一天直达**：当天从出发地到目的地（换乘按段计算）。
2. **两段式（最常见的最优解）**：第一天长途火车到过夜枢纽，住青旅；第二天白天大巴或火车到目的地铁路线上的某个站，再坐当地火车和最后一段。对每个「过夜枢纽 × 接入站」组合都拼一遍，比较「第一天车票 + 住宿 + 第二天大巴 + 当地火车 + 最后一段」的总和。
   - 变体：第一天到门户后，当晚再坐一小段大巴到住宿更便宜的小城过夜（例如日内瓦 → 安纳西）。
3. **卧铺夜车**：卧铺夜车（不是夜间大巴）直达目的地附近。
4. **飞机（作为基准）**。

### 第二天的大巴：越过门户，直接接上铁路线

这是两段式最省钱的地方。不要默认「大巴坐到门户城市（如日内瓦）」：
- 从过夜枢纽出发，对第 1 步列出的**每个接入站**都查一遍白天大巴（例如伯尔尼 → 日内瓦 / 安纳西 / 尚贝里 / 阿尔贝维尔 / 里昂）。
- **一定要用 Google 地图公交模式把「过夜枢纽 → 最后一个火车站」整段查一次**（选第二天的日期和出发时间，多看几个方案）。它会把长途大巴、大区班车、区域火车拼在一起，经常能找到「大巴到 A 城 → 大区班车到 B 站 → 区域火车」这种订票网站拼不出来的组合。再把它找到的每一段分别去官网核实价格和班次。（Google 地图的用法见下面「Google 地图：每条路线都要看」。）
- 「FlixBus 到更近的城市 + 大区班车 + 一小段区域火车」往往比「FlixBus 直接坐到铁路线上较远的站 + 长一点的火车」更快、更便宜、班次更多：区域火车按距离计价，大区班车按区段计价且很便宜。
- 跨境大巴可以一次省掉三样贵东西：贵的国家铁路（瑞士）、贵的门户城市、贵的门户接驳。大巴坐得越靠近目的地，后面的当地火车越便宜、换乘越少。
- 记下每条大巴线当天有几班：只有一班的要提醒风险，班次多的在「后备」里加分。
- 查清大巴下车点离火车站多远，以及大巴晚点时后面还有没有下一班火车。
- 把「门户接驳直达」（例如日内瓦机场 → 雪场的大巴）作为对比项一起列出。

### Google 地图：每条路线都要看

Google 地图的规划不总是最好，但它常常能拼出订票网站拼不出来的组合（Les Arcs 那次「伯尔尼 → 安纳西 → Y51 → 阿尔贝维尔」就是用户在 Google 地图上找到的）。所以：
- **每条候选路线的每一段都用 Google 地图公交模式查一次**，包括出发地 → 目的地全程、出发地 → 每个过夜枢纽、每个过夜枢纽 → 最后一个火车站、最后一个火车站 → 最终目的地。选对应的日期和出发时间。
- 把 Google 地图给出的方案和自己拼的方案对照：它找到了自己没想到的换乘点或交通方式，就把它加进候选并去官网核实；它给的方案明显更差，就忽略。在 HTML 页里用一句话写明「Google 地图推荐的是什么、和我们的方案比怎样」。
- 它只当参考，不当价格和时刻的来源：页面上出现「We don't have the most recent timetables for this area」时，时刻可能是旧的，一定要去运营方官网（FlixBus、SNCF Connect、大区交通网站）核实每一班。
- 实操：地址格式 `https://www.google.com/maps/dir/<起点>/<终点>/data=!4m6!4m5!2m3!6e0!7e2!8j<秒>!3e3?hl=en`，其中 `<秒>` 是把「当地出发时间」当作 UTC 算出的 Unix 时间戳（例如 2026-12-19 07:00 → 1797663600），`!3e3` 是公交模式。起终点要写完整地址（例如 `Gare Cornavin, 1201 Genève`），否则可能识别不出来。结果列表用文字提取常常读不到，直接截图放大左侧列表看；点「Details」看每一段。用户给的 Google 地图短链接在浏览器打开后会展开成完整路线。

### 发现更好的一段接法后，套用到所有路线

找到某一段更好的接法（例如「安纳西 → Y51 → 阿尔贝维尔」比「尚贝里 → TER」更快更便宜），要马上检查其他候选路线里有没有同一段或能接上这一段的，全部换成新接法重算（例如日内瓦过夜的方案也改成「日内瓦 → 安纳西 → Y51」，安纳西过夜的方案直接坐 Y51），不要只改用户问到的那一条。

### 第一天：看看能不能同价坐得更远

DB 的 Sparpreis Europa 去同一个国家的不同城市有时是同一个价（例如莱比锡 → 伯尔尼和莱比锡 → 日内瓦同为 41.26€）。拼两段式时，把同一班车上沿线更远的过夜城市也查一下价格：如果同价，就等于免费多坐一段。

### 其他贵的段落

任何一段火车明显贵的时候（典型情况：瑞士境内铁路），也查这一段的白天大巴，并搜「A → B 旁边的小镇 / 机场 / 边境另一侧的城镇」。

### 找干线的工具

1. **direkt-bahn.guru** —— 输入某个车站，地图上显示它所有直达目的地（含夜车）。对每个出发端枢纽查一遍。
2. **seat61.com**（The Man in Seat 61）—— 搜对应线路的页面，通常会写最佳路线、换乘点、以及在哪个官网买最便宜。
3. **夜车**：Back-on-Track 夜车地图、ÖBB Nightjet、European Sleeper、RegioJet、ČD/MÁV 的 EuroNight、季节性滑雪夜车（如 Travelski Night Express）等。**nightride.com** 能按日期列出夜车的每种铺位（座位、6 人 couchette、单人 sleeper 等）的实时起价，官网价格加载不出来时用它；新闻稿里的「dès 80€」通常是座位价，不是卧铺价。
4. **常规时刻表**：bahn.de、sbb.ch（欧洲时刻表也很全）、Google Maps 公交模式、Omio、Trainline。
5. **大巴（只看白天班次）**：FlixBus、BlaBlaCar Bus。
6. **大区班车和当地交通**：Google 地图公交模式、Rome2rio，以及当地大区交通网站（法国各大区 cars Région、Altibus；瑞士 PostAuto；意大利、奥地利的地区巴士等）。用来找第二天和最后一段的小交通，并查班次和按区段的票价。
7. **飞机**：Google Flights / Skyscanner；价格加上托运行李（滑雪装备另算）和往返机场的交通。

## 第 3 步：挑选路线

### 时间约束

- 每条路线都要按「最晚到达时间」检查能不能赶上，并考虑最后一段（缆车、站间巴士）的时间。
- **不要只给能赶上的方案就结束。** 如果有明显更便宜或更舒服的方案只是因为到达时间稍晚而被排除，要在结果里单独说明：「如果能放宽到 X 点，方案 Y 可以省 Z€」。到达时间往往没有用户第一次说的那么硬。
- 查第二天的车时，确认是否已售罄（法国 TER、TGV 经常售罄），并给出后备班次。

### 换乘与后备方案

换乘规则见「用户的固定情况」：按枢纽之间的段计算，每段 ≤3 次。换乘少但贵、换乘多但便宜的两类路线**都要列出来**。

用户常用的省钱策略：同一段里，换乘多、换乘时间短的便宜班次往往**比换乘少的贵班次更早出发**。按 DB 乘客权利，预计到达晚点 20 分钟及以上时，Sparpreis 等特价票的车次绑定会取消，可以改乘其他车次（以 DB 官网的 Fahrgastrechte 为准，跨境票要特别核实）。所以买早一班的便宜票，晚点了就改坐后面那班。

对每条短换乘路线（换乘 < 约 10 分钟，或要跨站台/车站，包括「大巴下车 → 火车站」）：
1. 标出每个换乘点的换乘时间。
2. 找出能当后备的更晚班次，写清楚「如果错过 X，可改乘 Y，大约几点到」。
3. 有后备的短换乘路线不扣分；没有后备、且会导致赶不上最晚到达时间的，要明确警告。

### 排序

挑约 5–7 条，优先级：
1. 能否在最晚到达时间前到
2. 总价（含住宿和最后一段）
3. 舒适度：晚上睡床 > 卧铺夜车；每段换乘少更好；后备班次多更好
4. 总时长

几条路线差价很小时（例如 5€ 以内），不要硬选一个，直接说清楚各自的取舍（最便宜 / 后备最多 / 含早餐）。

保证多样性：尽量包含最便宜的一条、最省事的一条、两段式（过夜枢纽）至少一条、门户接驳直达（作对比）、卧铺夜车（如果存在）、飞机基准（如果合理）、用户自己的方案（如果给了）。

**卧铺夜车不要因为贵就放进「排除」。** 只要它能按时到、不违反硬性条件，就作为正式方案排进去，写清楚它的优点和代价：优点通常是省一晚住宿、第二天不用早起赶车、上午就到、换乘最少、在车上睡觉；代价是价格和卧铺的睡眠质量。让用户自己权衡。「看过但排除的方案」只放违反硬性条件（赶不上、过夜大巴、某段换乘超过 3 次、没有住宿）或在价格、时间、舒适度上全面不如另一条的方案。

## 第 4 步：查价格（按日期范围）

### 多日期查价

- 优先用自带价格日历的功能：bahn.de 的「Unsere Bestpreise anzeigen」（按时段显示当天最低价）、Omio 日期选择器里的每日最低价、FlixBus 的日期价格条、Google Flights 的日期网格、SNCF Connect 结果页顶部的日期条。
- 详细的多来源对比至少做在「用户理想日期」和「范围内最便宜的那天」两天上。

### 每段查哪些来源

- **比价/代售平台（必查）**：Omio、Trainline。至少对最贵的那一段（通常是第一天的长途火车）查 Omio，和官网比；比价平台也能帮忙发现官网没显示的运营商和线路。
- **Interrail**：只卖通票和订座，不卖单程点对点车票。用户没有通票时不用来比价；它的行程规划器可以当时刻表交叉核对。在页脚用一句话说明。
- **相关的每个官网**：这段车涉及哪几国的铁路，就查哪几国的官网：
  - 德国 DB：bahn.de（选上 BahnCard 25）
  - 瑞士 SBB：sbb.ch
  - 法国 SNCF：sncf-connect.com
  - 奥地利 ÖBB / Nightjet：oebb.at、nightjet.com
  - 意大利：trenitalia.com、italotreno.com
  - 捷克 ČD：cd.cz；RegioJet：regiojet.com
  - 匈牙利 MÁV：jegy.mav.hu
  - 波兰 PKP Intercity：intercity.pl
  - 荷兰 NS International：nsinternational.com
  - 西班牙 Renfe：renfe.com
  - European Sleeper：europeansleeper.eu；Travelski Night Express：travelski.com
  - 大巴：flixbus.de、blablacar.de（Bus）
  - 最后一段的当地运营方（瑞士 PostAuto、法国 TER、法国大区班车 cars Région / Altibus、雪场缆车/接驳官网）

### 查价规则

- 白天车查**二等座**；卧铺夜车查**卧铺**（couchette 和 sleeper 各给最低价）。
- 德国境内能用 Deutschlandticket 覆盖的区域车段按 0 元计；也看看「区域车坐到某站 + 只买后面一段长途票」是否更便宜，但要说明分段的风险。
- 记录最便宜的可买票价，并标注票种（Sparpreis/Supersparpreis 不可退、Flex 可退）。
- 同时比较「联程票」和「分段买票」，分段要写明晚点没有保护的风险。
- 票还没开售的，写明「尚未开售」和大概何时开售。
- 每个价格记录查询时间。

### 怎么查（实操经验）

- 用当前 agent 能用的浏览器或网页工具查（Claude 里按用户的首选浏览器设置）；seat61 这类静态页直接抓网页就行。没有浏览器、只能搜索的 agent，要在结果里写明哪些价格没能实时查到。
- **bahn.de**：只用页面上的搜索界面，不要在页面里直接调用 bahn.de 的接口，也不要在一个脚本里连续点击多个时段，否则会被判定为机器人并封锁一段时间。一次点一个时段、等几秒再读。搜索结果页的地址可以改出发地/目的地/日期参数后重新打开；打开「Unsere Bestpreise anzeigen」看当天各时段最低价。DB 对法国国内段和部分国际 TGV 不显示价格，这时去 SNCF Connect 查。
- **sbb.ch**：查时刻表很快，地址格式 `https://www.sbb.ch/en?stops=<站名>_I<UIC码>~<站名>_I<UIC码>&day=YYYY-MM-DD&time=HH_MM&moment=dep|arr`；详细换乘加 `&trip=0_<序号>`。sbb.ch 显示的价格是瑞士半价卡价，不能用作德国/法国段的价格。
- **SNCF Connect**：可以用自然语言搜索地址，例如 `https://www.sncf-connect.com/home/search?userInput=Chambéry+Bourg-Saint-Maurice+samedi+19+décembre+12h30`，等十几秒结果页会出现价格和「Complet（售罄）」。
- **Omio**：用 omio.com（omio.de 是一家运动服装公司，不是比价平台）。打开 `https://www.omio.com/trains/<出发城市英文>/<目的城市英文>` 后点日期框，日历上直接显示每天最低价（默认不含折扣卡）；选好日期点 Search 能看到每班车由哪家卖。**Omio 会显示 ÖBB 的票价**，德国—奥地利/捷克方向 ÖBB 的特价票（Sparschiene）常常比 bahn.de 加 BahnCard 25 还便宜（例如德累斯顿 → 维也纳同一班车 ÖBB 29€，DB 49.99€），这类线路一定要看。
- **FlixBus**：搜索结果页加载慢时，可以在 flixbus 页面里调用它自己的搜索接口（城市 ID 先用 autocomplete 查），能批量拿到一个过夜枢纽到多个接入站的每班车时间、价格、换乘站。
- 遇到验证码、需要登录或被拦截：不要绕过，标记「未能查到」，给出搜索页链接让用户自己看。
- 绝不下单、不填写个人或支付信息。
- 控制工作量：每条路线优先查「最可能最便宜的官网」+ 运营方官网 + 一个比价平台，一般 2–4 个来源就够。

## 第 5 步：中途住宿（青旅）

青旅价格经常决定哪个过夜城市最好，但也最容易查错，所以按下面的方法逐家查：

- **来源：Hostelworld 和 Booking 两个都查**，同一家青旅在两边的价格和是否含早餐经常不一样，有时一边有房另一边没房。
- **必须按具体日期、具体房型查。** 不要用城市列表页上的「from …€」起价：Hostelworld 城市页的起价不按日期计算，地址里的日期参数也不一定生效，之前因此把一家当晚满房的青旅写成了 23.50€。要确认页面上显示的是目标日期、入住 1 人。
  - Hostelworld：属性页的房型列表按日期加载；也可以在 hostelworld 页面里调用它自己的房态接口（按青旅 ID、入住日期、人数查），一次比较多家。
  - Booking：搜索页带上 checkin/checkout/group_adults=1 和「Hostels」筛选，再进每家的属性页看房型表。
- **房型优先级：女生间 → 混合多人间。** 有女生间就报女生间的价；没有女生间才报混合间，并注明。
- 记录：青旅名字、房型（几人女生间）、两个平台各自的价格、是否含早餐、离第二天出发的火车站/大巴站的距离。总价用两边里更便宜的那个，并写明在哪里订。
- Booking 有只对登录会员显示的价格（Genius 等）。如果 `profile.md` 写了用户是 Booking 会员（例如 Genius），她看到的 Booking 价格常常比你查到的公开价低（伯尔尼那次是 39€ → 33€）：报价时写「Booking 公开价 X€，你登录后可能更低」，两个平台价格接近时优先建议用户去 Booking 登录后看。Hostelworld 价格可能不含当地城市税。
- 每个过夜城市至少查 2–3 家，评分太低、价格明显异常的房源（例如 1€ 或 1000€）跳过。
- **有青旅的城市优先于没有青旅的城市**；都有时比床位价和离车站距离。

## 第 6 步：算总价

每条路线的总价 = 各段车票/大巴票 + 中途青旅床位（如有）+ 最后一段（注意火车票联动的免费缆车/接驳）+ 额外费用（飞机行李、订座费、往返机场）。
总价用每段「最便宜的可信来源」相加，明细里保留各来源的价格。用脚本或计算器核一遍加法。

## 第 7 步：输出 JSON，用固定模板渲染对比页

页面的样式和排版已经固定在 `template/` 里，**不要手写 HTML 和 CSS**。你只需要按 `schema/trip.schema.json` 写一份行程 JSON，再用脚本把它渲染成页面。这样每次输出的只有数据，省 token，页面也每次一致。

### 1. 写 JSON

- 格式见 `schema/trip.schema.json`，完整示例见 `examples/leipzig-vienna.json`（莱比锡 → 维也纳，5 条方案）。不确定字段怎么写时，照着示例写。
- **方案编号由 `routes` 的顺序自动生成 A、B、C…**，所以把 routes 按推荐顺序排好就行，不用自己写编号。日期价格表和总览表也从 routes 自动生成，每列最低价自动标绿。
- 标「html」的字段可以用 `<b>`、`<a href=… target="_blank" rel="noopener">`、`<br>`，其他字段是纯文本。
- 文件名用行程名，例如 `leipzig-vienna.json`。

主要字段：

| 字段 | 说明 |
|---|---|
| `title` | 页面标题，两到四个词，例如「莱比锡到维也纳路线」 |
| `version` | 版本号，每次改版加 1 |
| `origin` / `destination` / `dateLabel` | 页头小字和大标题；需要别的写法时用 `eyebrow`、`heading` 覆盖 |
| `queriedAt` | 查询时间；页脚自动加「价格是查询时的快照，以官网为准」 |
| `intro` | html，页头说明：目标、硬性条件、关键思路 |
| `verdict.items` / `verdict.alert` | html，顶部结论和提示框（对上一版的更正、最便宜的日期等） |
| `relax` | html 数组，可选，「放宽条件能省多少」 |
| `dates` | 日期列；只有一天时不显示日期表 |
| `routes[]` | 每条方案，按推荐顺序排：`name`、`short`、`tag`、`total`、`price`、`effort`（green / blue / red）、`transfers`、`times`、`stay`、`backup`、`datePrices`、`legs[]`、`buy[]`、`notes[]` |
| `sections[]` | 可选的其他小节，例如「周六共用的后备车」 |
| `excluded[]` | 看过但排除的方案：`{name, why}` |
| `footer` | `paragraphs`（假设、查法、来源、Google 地图推荐了什么、哪些来源没查）和 `links` |

内容要求：

1. **顶部结论**：推荐哪条、哪天出发、为什么，最便宜/最省事各是哪条；用户给了自己的方案时说明它排第几。
2. **在哪里买最便宜**（`buy[]`）：每一段（车票、大巴、住宿）写清楚最便宜的购买渠道、价格、票种和链接，附上其他渠道的对比价；D-Ticket 之类免费覆盖的段写「0€（D-Ticket）」。
3. 每条方案写清后备（错过换乘改乘哪班、几点到）、中途青旅（名字、房型、两个平台的价格、是否含早餐、离车站距离）、最后一段（是否凭火车票免费）、注意事项（分段票风险、未开售、售罄、行李、订座、只有一班等）。
4. 页脚写查询时间、假设、青旅价格的查法、哪些来源没查和原因。

### 2. 渲染

在 skill 目录下运行（二选一，都不需要安装依赖）：

```bash
node scripts/render.mjs path/to/leipzig-vienna.json            # Node 18+
python3 scripts/render.py path/to/leipzig-vienna.json          # 只用标准库
```

生成的 `leipzig-vienna.html` 是一个独立文件：样式和脚本都已内联，直接用浏览器打开，或发给别人。脚本会先检查必需字段，有问题会报出是哪条方案的哪个字段；页面上出现红框「路线页渲染失败」也说明 JSON 写错了。

### 3. 交给用户

按所在环境选：

- **Claude（claude.ai / Claude 桌面端 / Claude Code）**：把渲染出的 HTML 用 Artifact 发布（同一趟行程改版时发布到同一个链接，并把 `version` 加 1）。不需要再加载 `artifact-design` skill，模板已经满足它的要求（浅色/深色主题、手机宽度、字体）。
  - 如果当前环境里没有 `scripts/`（例如只同步了 SKILL.md）：写一个页面外壳，把 JSON 放进 `<script type="application/json" id="trip-data">`，并引用 `style.css` 和 `render.js`，发布时用 Artifact 的 `files` 从模板 Artifact 复制这两个文件：`{"render.js": {"artifact": "https://claude.ai/artifact/83Dt3N16Yb3Wih2iKjnrAY", "path": "render.js"}, "style.css": {"artifact": "https://claude.ai/artifact/83Dt3N16Yb3Wih2iKjnrAY", "path": "style.css"}}`。外壳的写法见 `template/shell.html`（把内联的 `<style>` 和 `<script>` 换成 `<link rel="stylesheet" href="style.css">` 和 `<script src="render.js"></script>`）。
- **Cursor、Codex、Gemini CLI 等在本地运行的 agent**：把 JSON 和 HTML 存进项目的 `trips/` 目录，告诉用户文件路径。
- **ChatGPT（代码解释器）、Gemini 等只能上传文件的环境**：用 `python3 scripts/render.py` 渲染，把 HTML 作为文件发给用户下载。
- **完全不能运行代码的环境**：把 JSON 发给用户，并告诉用户在本地运行上面的渲染命令。

发布或发出文件后，在对话里用几句话总结推荐方案，不要把整张表再贴一遍。
